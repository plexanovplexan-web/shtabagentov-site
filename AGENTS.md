# Сайт «Штаб агентов» — правила для агентов

Действуют для всех, кто работает в этой папке: Claude Code, Codex и любой другой агент.

## 1. Что это за проект

Сайт `shtabagentov.com` — личный сайт владельца: проекты, обучение работе с ИИ-агентами, статьи и разборы,
запись на занятие. Размещение — GitHub Pages из папки `docs/` этого репозитория.

**Репозиторий открытый: всё, что лежит в папке, видно всем.**

## 2. Что лежит в папке

|---|---|

## 3. Правила проекта

1. **Ничего внутреннего.** В эту папку не кладут акты, журналы, квитанции, решения, переписку, черновики,
   выгрузки, адреса чатов, ID ботов и чатов, имена клиентов, суммы и любые секреты. Рабочие документы сайта
   ведутся в проекте «Работа» (`D:\repos\cowork`), сюда попадает только готовый результат.
2. **Публикация — решение владельца.** Отправка в `main` меняет живой сайт. Новые разделы, цены, тексты от
   имени владельца и кнопка записи выпускаются только по его слову в чате исполнителя.
3. **Очерёдность работ** задаёт штаб проекта «Работа»: `D:\repos\sync-hub\docs\cowork-priorities-2026-11-17.md`,
   раздел А. Исполнитель — Codex «Работа», по правилам «Работы».
4. **Перед отправкой проверить глазами**: страница открывается локально, ссылки и картинки на месте, в файлах
   нет ничего из пункта 1.
5. **Язык** — русский: тексты сайта, комментарии в коде, ответы владельцу. Просто, но без потери точности.

## Контур синхронизации

Как работа агента попадает на GitHub. Механизм общий для всех проектов
владельца и живёт в хабе `D:\repos\sync-hub` (репозиторий
`plexanovplexan-web/Sync-Hub`, описание — его `README.md`). В проекте от него
два файла — `sync.config.json` (настройки) и `sync.bat` (кнопка) — и этот
раздел с правилами. Значения, которые у каждого проекта свои (папка,
репозиторий, цель отправки, порядок чтения), — ниже, в «Параметрах контура».

Три части, ни одна не заменяет другую:

| Часть | Кто | Когда работает |
|---|---|---|
| Агент | Claude Code или Codex в открытой сессии: пишет файлы в папку проекта и отчитывается | только пока сессия открыта |
| Хаб | кнопка `sync.bat` и сторож `watch.bat`, общие для всех проектов | сторож — пока открыто его окно |
| Источник правды | ветка `main` репозитория на GitHub | всегда |

«Агент по синхронизации» — это роль внутри сессии, а не служба. Закрыт чат —
никто ничего не сохраняет. Поэтому агент пишет на диск по ходу работы, а не в
конце. Отчёт о каждой отправке движок отправляет сам — боту синхронизации
(n8n → PostgreSQL → Telegram) и на доску; в проекте для этого делать ничего
не нужно.

Что контур гарантирует: всё, что лежит в папке, уедет на GitHub без участия
агента. Чего не гарантирует: он не знает о работе, оставшейся в сессии, и не
защищает от одновременной записи двух агентов в один файл — от тихой потери
правки защищает правило Б, а не техника.

### А. Когда сохранять

Правило: **сессия агента — черновик, папка на диске — результат.** Всё, что
существует только в сессии, считается несуществующим.

1. **После каждой закрытой единицы работы** — задача, документ, раздел,
   принятое решение. Не «в конце сессии» и не «когда попросят».
2. **Одно логическое изменение — одна запись.** Сторож собирает пачку по
   45 секундам тишины; дробить одну правку на пять записей — значит получить
   пять коммитов ни о чём.
3. **На диск уходит только законченное.** Черновик, недоделанный расчёт,
   непроверенная цифра остаются в сессии. Половинчатое состояние в папке
   недопустимо: сторож отправит его как есть.
4. **Перед длинной работой** (обход сайта, разбор данных, большой анализ)
   агент сначала сохраняет то, что уже готово: сессия может оборваться.
5. **По команде владельца «сохраняйся»** — то же самое немедленно, чем бы
   агент ни был занят.

Дописывается всё, что задача сдвинула: файл состояния проекта, задачник, при
решении — запись в реестре решений, при релизе — журнал изменений.

Разрешение владельца нужно на действия в боевых системах и на изменение
плана. Запись результата уже выполненной и принятой работы (акт, статус,
журнал) разрешения не требует и не откладывается: «жду твоего да на
запись» для сделанного — нарушение этого правила. Если в папке параллельно
пишет другой агент, откладывается только конфликтующий файл (правило Б);
новый файл с актом создаётся сразу.

### Б. Сначала прочитать, потом писать

Файл в папке мог измениться без агента: его правил владелец, второй агент или
это остаток прошлой сессии после `git pull`. Поэтому перед записью в
существующий файл агент **обязан прочитать его с диска** и сравнить со своей
копией.

- Совпадает — писать молча.
- Не совпадает — **не перезаписывать**. Сообщить владельцу: какой файл, чем
  отличается, когда менялся, — и предложить выбор: (а) взять версию с диска за
  основу и внести правку поверх; (б) оставить диск как есть, показать свою
  версию отдельно; (в) собрать вручную из обоих кусков. Решает владелец.

Исключение — файлы, которые агент создаёт впервые: читать неоткуда.

### В. Отметки в чате

Контур не работает молча. Отметки: чтение, запись (два состояния), проверка,
итог сессии. Номер записи считается внутри одной сессии, с №1. Нет отметки —
считается, что сохранения не было. Одна азбука знаков везде — в чате, в боте и
на доске: `+` новый файл, `~` изменён, `−` удалён; ✅ уехало, ⏳ ждёт сторожа,
⛔ остановлено, 🔀 PR слит.

**ЧТЕНИЕ** — в начале сессии, когда агент загрузил контекст из папки:

```
━━ КОНТУР СИНХРОНИЗАЦИИ · ЧТЕНИЕ · <дата ЧЧ:ММ> ━━
Папка:   <путь проекта>
Сверка:  main = origin/main = <sha> ✔   (папка совпадает с GitHub; fetch <ЧЧ:ММ>)
Прочитано: <список файлов>
Состояние: <одна строка: где проект>
```

**ЗАПИСЬ** — после каждой записи на диск. В чате — одна строка; «Задача»,
«Проверил» и «Основание» — в `.sync-note.md` (ниже), движок кладёт их в отчёт и
в бота. Сразу после записи — ⏳; когда запись уехала — ✅ по отчёту движка
`sync-hub\reports\<проект>\last.json`, GitHub для этого не нужен:

```
⏳ ЗАПИСЬ №<N> · <проект> → <цель> · ждёт сторожа · <задача одной строкой>
✅ ЗАПИСЬ №<N> · <проект> → <направление> · <sha> · <N> файлов · <k>/<k> · CHISTO · <ЧЧ:ММ>
```

Полный блок — при ⛔, при предупреждениях движка и по команде «проверь»:

```
✅ КОНТУР СИНХРОНИЗАЦИИ · ЗАПИСЬ №<N> · <проект> — уехало → <направление> · <sha>
Задача:   <ID> · <зачем>
Записал:  ~ <путь> — что изменилось
Проверил: <чем>
Основание: раздел «Контур синхронизации» AGENTS.md, пункт «А. Когда сохранять» (правила v4 · источник sync-hub\templates\agents-section.md)
📄 Файлы: <N> (новых <a> · изменено <m> · удалено <d>)
  ~ <путь>
🔍 Проверки: <k> из <k> · секреты/allowlist/мусор: CHISTO
📡 GitHub: CONFIRMED (<направление>) · <ссылка на коммит или PR из отчёта>
📝 <текст коммита>
⏱ <дд.мм.гггг чч:мм:сс> · <сек> с · <сторож|кнопка> · <машина> · движок <версия>
```

Если движок остановился — та же шапка с ⛔, шаг и причина из отчёта
(`stopped_at`, `stop_reason`) и что агент предлагает сделать. Для цели
`branch` направление — `sync/<дата>` и ссылка на PR, после merge — 🔀 слит.

**«Задача», «Проверил» и «Основание»** агент перед записью кладёт в корень
репозитория файлом `.sync-note.md` — движок их сам не знает. «Основание»
называет правило записи и где оно лежит: раздел «Контур синхронизации» в
`AGENTS.md` того же проекта, пункт «А»; версия — в маркере `SYNC-CONTOUR:BEGIN`,
источник — `sync-hub\templates\agents-section.md`:

```
Задача: <ID> · <зачем правка, одной строкой>
Проверил: <чем проверено>
Основание: раздел «Контур синхронизации» AGENTS.md, пункт «А. Когда сохранять» (правила v4 · источник sync-hub\templates\agents-section.md)
```

Движок вставляет текст в отчёт под шапкой ✅/⛔ и удаляет файл после
подтверждённого коммита; при остановке оставляет для повтора. Файл в
`.gitignore`, в коммит не попадает, кириллица в нём безопасна. Предел — 800
знаков, длиннее движок обрежет молча. Нет файла — бот покажет блок движка без
этих строк.

**Время в отметках.** Дату последнего `git fetch` брать по времени файла
`.git\FETCH_HEAD`, а не `refs\remotes\origin\main`: движок делает
`git fetch origin --prune` при каждом запуске, но указатель переписывается,
только если он сдвинулся. Время файлов приходит в UTC — в отметке показывать
местное время владельца; в отчёте движка (`last.json`) время уже со смещением.

**ПРОВЕРКА** — когда агент сверяет с GitHub, ничего не записывая (по команде
«проверь»): это ✅-блок записи №N; если записей несколько — по строке на
каждую. Если папка и GitHub разошлись — так и писать: «не уехало», назвать
причину (сторож не запущен, отправка остановлена) и не продолжать работу
поверх, пока владелец не решит.

**ИТОГ СЕССИИ** — по команде «итог» или в последнем ответе дня:

```
━━ КОНТУР СИНХРОНИЗАЦИИ · ИТОГ СЕССИИ · <дата> ━━
Записей: <N> · уехало: <N> · не уехало: <N> · файлов: <N>
№1 ✅ <sha> — <задача> · <N> файлов · PR открыт | 🔀 слит
№2 ⏳ ждёт сторожа — <задача> · <N> файлов
Открытые PR: нет | <ветка · ссылка>
```

### Г. Старт новой сессии

Контекст берётся **только** из файлов рабочей папки; чат, индекс проекта и
память агента источником не являются. Порядок:

0. сверить `.git/refs/heads/main` с `.git/refs/remotes/origin/main` —
   разошлись, сказать владельцу до начала работы. Проверить `.git/HEAD`: он
   должен указывать на главную ветку; если на `sync/*` — последняя отправка
   ещё не слита, сказать об открытом PR;
1. `AGENTS.md` — этот файл;
2. дальше — порядок чтения из «Параметров контура» ниже.

Репозиторий с GitHub агент не выкачивает — он приватный. GitHub нужен для
другого: резервная копия, второй агент и вторая машина, история и откат, CI,
точка сверки. Правило: **папка — рабочий контекст, `main` — доказательство,
что контекст не потерян.**

### Д. Кнопку и сторож агент не запускает

И не делает вид, что запустил: доступа к Windows у него нет. Отправку
выполняет сторож из хаба или владелец кнопкой `sync.bat`. Как агент проверяет,
что уехало: `refs` в `.git` и последний отчёт движка
`sync-hub\reports\<проект>\last.json`. Если в отчёте `exit_code = 2`, сторож
заморозил проект и не смотрит на него, пока владелец не нажмёт `R` в окне
сторожа, — сообщить об этом сразу, а не ждать.

### Границы

Не удалять существующие файлы без списка на утверждение; не переписывать
документацию молча; не менять скрипты хаба (`push.ps1`, `watch.ps1`), его
конфиги и воркфлоу n8n; не коммитить до разрешения владельца. Правки в
`sync.config.json` и в этом разделе — только по решению владельца: раздел
дословно повторяет источник `sync-hub\templates\agents-section.md`, и любая
правка здесь будет замечена сверкой и потеряна при следующем обновлении.

## Работай до результата, не раздувай задачу

Требование владельца, постоянное: одни правила работы во всех проектах — для каждого
агента: Codex, Claude, любой сессии. Блок между маркерами — дословная копия единого
источника `sync-hub\templates\work-rules.md`; здесь его не править. Своё у проекта —
в «Дополнениях этого проекта к правилам работы» сразу после блока. Текст
сформулировали агенты Cerebrum с проектным Claude 30.10.2026; для всех проектов
утверждён владельцем кнопками 30.10.2026. Быстрый путь (правила 12–16) — по разбору
задержки в «Работе», утверждён владельцем кнопками 31.10.2026. Правило 17 — требование
владельца 09.11.2026 после разбора установки в «Балансах». Правило 18 — решение
владельца 17.11.2026 после остановки в «Балансах», о которой он узнал через 50 минут.

Применяй к порученной задаче в пределах действующих разрешений и правил проекта. Эта
инструкция не отменяет безопасность, обязательный контроль, запреты и точку
остановки. **Правила проекта, которые строже, — главнее:** разрешение на шаг, гейт,
подтверждение перед отправкой, команды, которые выполняет владелец. Для правки
быстрого класса (правило 12) это относится к разрешениям, запретам и гейтам проекта,
но не к требованиям полного класса. Правило 17 действует поверх строгих условий
остановки проекта: некритичное событие не становится STOP из-за общей формулировки
вроде «любой diff — STOP».

1. **Держи цель.** Кратко назови результат для пользователя, проверяемый критерий
   готовности и границы поручения. Используй уже согласованные условия без
   повторного утверждения. Если поручены только документы, заверши проверяемый
   документ; не выдавай его за работающее внедрение.
2. **Выбирай короткий достаточный путь.** Сохраняй обязательные гарантии из
   действующих требований, контрактов и решений. Переиспользуй актуальные решения и
   применимые результаты проверок. Не строй универсальную платформу для частной
   задачи и не переноси старое заключение на непроверенное изменение.
3. **Обосновывай усложнение.** Новый компонент, документ или проверка должны
   закрывать конкретный критерий, обязательное требование или существенный риск
   текущего результата. Покажи, почему имеющегося решения недостаточно и что
   добавится к остаточной работе. Не превращай возможное улучшение в обязательную
   зависимость.
4. **Разделяй необходимое и отложенное.** Необязательные улучшения кратко отмечай
   отдельно. Новый существенный риск оцени по фактам: опасное зависимое действие
   останови, безопасную работу продолжай. Смену цели, принятых гарантий, модели
   угроз, прав или расходов согласовывай в пределах полномочий; молча расширять
   задачу нельзя.
5. **Завершай рабочий цикл сам.** Подготовка, обязательная консультация, проверка,
   исправление существенных замечаний и сохранение — одно законченное разрешённое
   поручение. Не возвращай владельцу каждую мелкую правку, новую редакцию или
   рутинную проверку отдельной командой. Явную границу завершения соблюдай.
6. **Проверяй соразмерно риску.** Для проверки назови ожидаемое свидетельство.
   Повторяй её при изменении, новой находке, непокрытом риске либо обязательном
   требовании. Не запускай повторный круг без причины. Нужную независимость
   сохраняй; косметика не блокирует достаточный результат, критический дефект нельзя
   скрыть ради скорости.
7. **Работай с советником предметно.** Когда консультация обязательна, обсуждай
   текущую редакцию и вопросы пакетом. Проси проверить достаточность решения и
   необходимость новых слоёв. Свежий обязательный совет не заменяй старым; выводы
   проверь сам. Консультация не равна независимой проверке или разрешению владельца.
8. **Выходи из бесплодных повторов.** Если круг не уменьшает существенную
   неопределённость, назови повторяющуюся причину и измени подход внутри
   разрешённого. Не создавай очередную редакцию ради движения. Сохраняй обязательную
   историю; новый документ нужен для результата, а не как новый ритуал управления.
9. **Стремись к проверяемому результату.** Получай его при первой разрешённой
   возможности. Если запуск или нужные данные запрещены, не обходи запрет и не
   заменяй недостающее свидетельство разрастанием архитектуры. Доведи допустимую
   подготовку до конкретного блокера. Один запрет не останавливает остальные
   полезные разрешённые шаги.
10. **Обращайся к владельцу только по делу.** Сначала выполни всё полезное, не
    зависящее от ответа. Затем задай минимум вопросов — кнопками по шаблону общения,
    с вариантами и рекомендуемым выбором, — если без ответа нельзя продолжить. Уже
    данное разрешение не переспрашивай; молчание разрешением не считай.
11. **Отчитывайся коротко.** Покажи: что готово, чем подтверждено, что теперь
    известно, что реально осталось и ближайший допустимый шаг. Различай подготовку,
    проверку и внедрение. Время активной работы отделяй от ожидания и полного
    завершения; сроки и проценты не выдумывай. Обязательные документы, контроль,
    защиту секретов и проверку сохранения соблюдай. По готовности закончи поручение
    без новых вымышленных задач.

### Быстрый путь

12. **Назови класс риска до начала работы** — одной строкой в первом ответе на
    поручение; владелец может поправить.
    - **Быстрый:** правка откатывается прежней версией и не трогает настоящих
      клиентов, деньги, чужие данные и секреты — тексты, эмодзи, подписи,
      оформление, правка в закрытом тесте, документы. Порядок: правка → проверка →
      применение штатным каналом → проверка цели → при сбое откат прежней версией,
      одним поручением. Консультация — один круг до 10 минут; нет ответа — дальше
      с пометкой «без консультации». Новые версии — коммитами, без новых папок и
      копий.
    - **Полный:** боевые данные и клиенты, деньги, удаление, миграции, секреты,
      необратимое — порядок проекта: допуски, удержание, восстановление.

    Требования полного класса к быстрому не применяй. Смешанную правку раздели:
    быструю часть выпусти отдельно, если её можно отделить без новой сборки; иначе
    — полный класс или явное решение владельца о риске.
13. **Веди поручение до видимого результата.** «Готово, когда» — то, что владелец
    увидит сам: в боте, на сайте, в файле, в отчёте. Применение и проверка цели — в
    том же поручении, если владелец может разрешить их сейчас. Документ — результат,
    только когда владелец просил документ. Предлагая следующее поручение, сведи в
    него все шаги до результата, а не следующий подшаг.
14. **Разрешение — в чате исполнителя.** Исполнитель получает разрешение владельца в
    своём чате, а не пересказом из другого. Всё, что исполнитель сверяет, — ID, SHA,
    пределы, откат — вписывай в готовый текст разрешения, который владелец копирует;
    повторять это вручную от владельца не требуй. Чего не хватает — один вопрос
    кнопками, а не STOP.
15. **Иди штатным каналом.** Правку, которую делают в интерфейсе системы или через
    его API, — редактор n8n, BotFather, панель хостинга, GitHub, гейт проекта —
    делай там. Обходной канал — SQL в служебную базу, скрипт по SSH, импорт
    целиком — только когда штатного нет; скажи почему.
16. **Останавливай затягивание.** Признаки: два поручения подряд без шага к
    видимому результату; один блокер в двух актах подряд; второй круг консультации
    по одному вопросу. Тогда новый документ не пиши, а дай владельцу: что
    блокирует; одно решение или действие, которое его снимет, — кнопками,
    рекомендуемое первым; одно поручение до результата после этого решения.

### Остановки

17. **Останавливайся только на критичном.** STOP — только при одном из признаков:
    - не предусмотренное допуском изменение кода, SQL, параметров, учётных данных,
      входа (триггера), связей или настроек выполнения;
    - запись в базу, деньги или отправка наружу с неизвестным итогом; ошибка базы;
      расхождение суммы;
    - публикация или включение версии, чьё содержимое не сверено;
    - чужое подключение или чужое изменение критичного;
    - блокировка платформы или фильтра безопасности — её не обходят, решает владелец.

    Остальное некритично: не STOP, а запись в акт и продолжение того же поручения,
    без нового допуска:
    - служебная сериализация системы — расположение, служебные ID, `null` вместо `[]`,
      номера и даты версий, явные значения по умолчанию;
    - сбой инструмента, если итог устанавливается чтением: чтение повторяй; запись
      повторяй только при доказанном нестарте;
    - новая версия неизвестного происхождения, если строгая сверка критичного
      прошла: она становится исходной;
    - отклонение от согласованного способа, пока система выключена и итог проходит
      ту же строгую сверку критичного.

    Сомневаешься в классе — решает строгая сверка критичного. Допуски пиши так же:
    условия STOP — только критичные признаки, некритичное разрешено заранее по видам.
    Окно времени задавай по реальным пределам — бэкап, срок проверки архива,
    присутствие владельца, — а не «до вечера».

18. **Остановился — позови.** Если ход кончается, а продолжить можно только после
    владельца — нужна его строка согласия, ответ, действие руками или возврат
    инструмента, — запись об остановке уходит с красной карточкой-зовом. Первая
    строка `.sync-note.md`: `Задача: 🔴 Нужен владелец: <одно действие>; <пояснение>`.
    Сразу, в той же записи, что и акт остановки: после конца хода агент сам не
    вернётся, и позвать будет некому. Результат установлен и ждёт проверки самого
    владельца — зелёная: `Задача: 🟢 Готово — прими: <один тест>`.
    - действие начинается с глагола и понятно без чтения чата; фраза для вставки —
      в «ёлочках» в конце действия; где отвечать — строкой `Где:`;
    - одна остановка — одна карточка; зовёт тот, кто остановился; координатор зовёт
      только по своей остановке;
    - без сумм, строк базы, имён, ID и секретов; карточка ничего не разрешает и не
      заменяет ответ в чате;
    - не ставится с 00:00 до 09:00 по времени владельца и пока владелец сам ведёт
      рабочее окно;
    - агент ещё работает и ждёт владельца параллельно — кружок на первой отправке
      после десяти минут ожидания.

    Формат карточки — раздел 8 README хаба (`sync-hub\README.md`); заметка
    `.sync-note.md` — правило В раздела «Контур синхронизации».

## Шаблон общения

Один шаблон ответа владельцу во всех проектах. Копия `sync-hub\templates\answer-template.md` — здесь не править; своё — в «Дополнениях этого проекта к шаблону общения» после блока.

### 1. Ответ сверху вниз

1. **Вывод** — 2–3 строки: что получилось и что даёт.
2. **Где мы** — фаза или раздел, зачем шаг; тест, бой или только файлы.
3. **Суть** — нужное для решения: факты, таблица, доказательства, строка связки (п. 4).
4. **Тест** — одно действие владельца и что он увидит.
5. **🟩 Готово**, **🟥 Нужен ты** — по ситуации.
6. **Отметки записей** — по правилу В контура; успешная отправка — одна строка.
7. **Состояние** — 3–5 строк.
8. **🟨 Дальше** — всегда, последним, минимум два действия; в карточке — срок до конца фазы.

Карточка 🟨 — в каждом сообщении, которым заканчивается ход: и в коротком ответе, и в промежуточном. Сообщение посреди работы, после которого агент сам продолжает ход, — вывод, «где мы», строка связки и строка «🟨 Дальше: …».

### 2. Правила

- **Подача.** По-русски, просто, без потери точности; внутренний код — после слов. Статус — подготовлено / внедрено / проверено; готовые тесты — не пройденные, отчёт другого агента — не своя проверка. Число — с источником, датой и фильтром; проценты — при утверждённом перечне; сроки — агент / владелец / ожидание, без основания — «не оценено». Документы — файлами целиком.
- **Тест** проверяет цель, а не слой; ожидаемая неудача — заранее; без изменений — «наблюдаемых изменений нет».
- **🟩** — только проверенное, с доказательством; работа Claude — после проверки Codex.
- **🟥** — только когда без владельца нельзя: зачем; где и под какой учётной записью; что сделать (пароль в чат не просить); что получится и где остановиться при ошибке; что изменится. Ответ владельца после действия — поручением в 🟨.
- **Вопросы** — кнопками: 2–4 варианта, рекомендуемый первым с «(Рекомендую)», строка последствий, не больше 4. Решённое и «продолжать ли?» не спрашивать.
- Разрешённый шаг — сейчас, не обещанием. Рекомендация — не разрешение: допуск — через 🟥. Пароли, ключи, токены — никогда.

### 3. Состояние и 🟨 Дальше

```makefile
━━ ОСТАТОК ДО <ЦЕЛЬ НАПРАВЛЕНИЯ> ━━
Сейчас:        <подготовлено / внедрено / проверено>
Осталось:      <шаги до приёмки; блокер>
Нужно от тебя: <решение или действие | «ничего» — не разрешение>
Документация:  <записано: файлы и sha | не записано: что>
```

Пятая строка — по нужде: «Связка с Claude», «Граница» или «Проверка». Без изменений — «Состояние: без изменений».

```markdown
> 🟨 **Дальше: <глагол + что>**
>
> 🎯 **Цель** — <чего ты хочешь, твоими словами>
> ⏱ **До конца фазы** — <≈ работа агентов; реальная дата; от тебя — сколько (основание) | «не оценено: чего не хватает»>
> 🚧 **Блокирует** — <что мешает дойти до видимого результата | «ничего»>
> ⚡ **1. Рекомендую** — <действие и почему это самый короткий путь до видимого результата>
> 🔀 **2. Или** — <другое действие и чем оно отличается>
> 👉 **От тебя** — <формула>
```

В цитате нет кодов и путей. ⏱ — оценка до приёмки фазы, названной в цели и в заголовке состояния, а не до конца шага: диапазон работы агентов, реальная дата, участие владельца, в скобках основание; без основания — «не оценено» и чего не хватает для оценки, срок не выдумывать. Оценка та же — «без изменений (от <дата>)»; изменилась — новая и одна причина; разбивка по шагам — в состоянии, когда оценка дана впервые или изменилась; фаза принята — «фаза закрыта». 🚧 — что мешает дойти до видимого результата и чем это снимается; нет — «ничего». Действий — всегда минимум два, по номерам, каждое одной строкой и понятно без чтения ответа выше: владелец выбирает, а не думает. Первое — рекомендуемое: самый короткий путь до видимого результата и почему. Второе — настоящая альтернатива; если её нет — следующий шаг после первого или «подождать» с тем, что будет. Третье и дальше — по нужде, тем же видом. Формулы 👉: «Ничего — я продолжаю: …» · «Ничего — Клод работает, проверю <когда>» (его чат прочитан в этом ходе) · «Скопируй поручение — без него этап не начинаю» · «Работа завершена; дальше — скопируй поручение» · «Сначала 🟥». 👉, 🟥 и «Нужно от тебя» не спорят.

Под цитатой — свой блок для каждого действия, где владельцу нужно что-то вставить: «📋 **1 — поручение** (сюда | в Codex «<проект>» | Claude проекта)», «📋 **2 — …**» и блок `text`; действию без текста блок не нужен. Требования к блоку: проект и папка → результат и все шаги до него, с применением, если владелец может разрешить его сейчас → исполнитель и канал → чего не трогать → когда остановиться — только реальные причины → «Готово, когда <что владелец увидит сам>» и что вернуть → «на этом остановись». Документ — результатом, только если владелец просил документ. Понятно в новой сессии; внутри — только текст агенту, без `<подставь…>`. Агент продолжает сам — над блоком «Вставлять не нужно — это команда для новой сессии». В чат Claude — только при ⛔.

**Проверка перед отправкой:** последнее в ответе — карточка 🟨, в ней строка ⏱, минимум два действия и блоки к ним. Нет — допиши до отправки. После сжатия контекста или в новой сессии формат берётся из этого раздела, а не из памяти разговора.
